# 为什么每一代新芯片都会带来新的算子开发工作？

> 新芯片发布后，旧代码通常还能运行，但“能够运行”和“充分发挥硬件性能”之间，往往隔着一整轮算子适配与优化。

如果持续关注 GPU、AI 芯片和大模型基础设施，会看到一个很稳定的现象：几乎每发布一代新芯片，cuBLAS、cuDNN、CUTLASS、Triton、FlashAttention、vLLM、TensorRT 等软件栈都会紧接着更新；芯片厂商、框架团队和模型公司也会重新做性能测试，甚至重写一部分底层 kernel。

于是很自然地会产生一个问题：

**是不是每出一代芯片，做算子开发的人就又有活了？**

答案基本是肯定的，但需要补上一个重要限定：

**新一代芯片并不意味着所有算子都要推倒重写，而是意味着计算、访存和通信的成本模型发生了变化，高性能实现需要重新寻找最优解。**

这也是算子开发长期存在的根本原因。

## 一、先说清楚：什么是算子开发？

深度学习模型在代码中看起来可能只有几行：

```python
x = linear(x)
x = rms_norm(x)
x = attention(q, k, v)
```

但这些高层操作最终需要被拆成 GPU 能执行的底层程序，也就是 kernel。矩阵乘法、归一化、激活函数、Attention、量化、KV Cache 更新，都可以由一个或多个 kernel 完成。

所谓算子开发，通常不只是“把公式翻译成 CUDA”。真正的工作包括：

1. 正确地实现计算语义；
2. 根据硬件组织线程、warp 和线程块；
3. 设计数据在寄存器、共享内存、缓存和显存之间的移动方式；
4. 选择合适的数据类型和 Tensor Core 路径；
5. 融合多个操作，减少中间结果和 kernel 启动；
6. 针对不同输入形状选择不同实现；
7. 把算子接入 PyTorch、JAX、TensorRT、vLLM 等上层系统；
8. 用真实模型证明单算子优化确实改善了端到端性能。

因此，算子开发本质上是一项跨层工作：上面连接模型和框架，下面连接编译器、指令集和芯片微架构。

> **简单例子：RMSNorm**  
> 高层代码可能只是 `y = x / sqrt(mean(x²) + eps) * weight`。直接实现时，平方、求和、开方、除法和乘权重可能形成多个步骤；优化实现会尽量把它们放进一个 kernel，避免中间张量反复写回显存。公式没有改变，但执行方式变了。

## 二、为什么新芯片会创造新的算子工作？

### 原因一：新硬件能力不会自动变成应用性能

新一代 GPU 往往会加入新的指令、数据类型、存储层级或异步执行机制。例如：

- **Ampere** 强化了 Tensor Core，带来 TF32、BF16、结构化稀疏和新的异步数据搬运能力；
- **Hopper** 引入 FP8 Transformer Engine，并强化了 TMA、warpgroup 级矩阵运算和异步流水；
- **Blackwell** 继续推进第五代 Tensor Core、FP4 和更细粒度的低精度缩放，同时进一步强化系统级互联与大模型执行能力。

这些能力只有在软件主动使用时才会产生价值。

一个为 A100 编写的 CUDA GEMM，通常可以直接或重新编译后运行在 H100 上。但如果它仍沿用旧的数据搬运方式和矩阵指令，就只能获得“新芯片运行旧实现”的性能，而不是“H100 应有的性能”。

这和购买一辆新赛车却继续使用旧轮胎、旧变速策略类似：发动机更强了，但整套配合没有改变，最终速度不会按纸面参数增长。

> **简单例子：旧矩阵乘运行在新 GPU 上**  
> 某个 FP16 GEMM 在旧 GPU 上使用普通 CUDA Core。把它重新编译后放到支持更强 Tensor Core 的新 GPU 上，程序通常仍能得到正确答案；但如果实现没有切换到新的矩阵指令，它就可能只是“跑在新卡上的旧算法”，而不是充分利用新硬件。

所以新芯片发布后的第一批工作，通常包括：

- 编译器增加新架构目标；
- PTX、SASS 和内建函数支持新指令；
- CUTLASS、cuBLAS、cuDNN 增加新 kernel；
- Triton、TVM 等编译器增加新的后端和调度规则；
- 框架和推理引擎增加新的 dtype、量化格式与算子路径。

### 原因二：最优 tile 和流水线会改变

高性能 kernel 的核心问题之一，是如何把一个大计算任务切成适合硬件执行的小块，也就是 tile（计算分块）。

一个 tile 太小，数据复用不足，Tensor Core 吃不饱；一个 tile 太大，又可能占用太多寄存器和共享内存，导致同一 SM 上能同时运行的线程块减少。

每代芯片都可能改变以下条件：

- Tensor Core 支持的指令形态与数据类型；
- 每个 SM 的寄存器和共享内存容量；
- L1、L2 和外部内存的带宽与延迟；
- 异步拷贝和同步机制；
- warp、warpgroup、CTA 和 cluster 的协作方式；
- 每个 SM 可驻留的 warp 或 CTA 数量；
- 计算吞吐与内存带宽的比例。

因此，上一代最优的配置到了下一代未必仍然最优。开发者可能需要重新选择：

- CTA tile 和 warp tile；
- 每个线程计算多少元素；
- pipeline stage 数量；
- producer warp 与 consumer warp 的分工；
- shared memory swizzle 和数据布局；
- split-K、persistent kernel 等调度方式；
- 不同 shape 应该分派到哪个 kernel。

这不是简单修改一个编译参数，而是重新平衡并行度、数据复用、片上资源和访存开销。

> **简单例子：tile 不是越大越好**  
> 假设一个线程块一次计算 `128×128` 的输出块，数据复用很好，但会占用很多共享内存；如果改成 `64×64`，单块复用下降，却可能让更多线程块同时驻留在 SM 上。哪一种更快，要看芯片资源、矩阵形状和实际 occupancy（SM 上活跃线程束的占用率），而不能只凭“更大的块复用更多”判断。

### 原因三：新的数据类型会带来一整条软件链

低精度是近年来 GPU 演进的重要方向。从 FP32 到 TF32、FP16、BF16、FP8，再到 FP4，纸面吞吐不断提高，但位数更低也意味着数值范围和精度更难控制。

以 FP4 为例，真正可用的实现通常不只是一个“FP4 GEMM”，而是一整条路径：

```text
高精度权重
  → 分块量化
  → 计算缩放因子
  → FP4 打包与存储
  → Tensor Core 矩阵乘
  → 反量化或缩放
  → bias / activation / residual 等后处理
```

如果量化、解包和反量化开销过高，即使矩阵乘本身很快，端到端也可能没有收益。因此，新精度往往会同时产生以下工作：

- 量化格式和 scaling 策略；
- 数据布局与打包 kernel；
- 低精度 GEMM；
- fused epilogue（矩阵乘后处理融合）；
- 精度评测和异常值处理；
- 模型权重转换工具；
- 框架和推理引擎的 dtype 支持。

这说明新硬件能力很少是一个孤立功能，它通常需要从模型到 kernel 再到运行时的整条软件链配合。

> **简单例子：低精度不一定自动更快**  
> 假设 FP4 矩阵乘的理论吞吐是 FP16 的数倍，但每一层之前都要额外启动 kernel 做量化、计算 scale 和数据打包。对于很小的矩阵，这些准备工作可能比矩阵乘本身还贵。只有把转换与 GEMM 或后处理融合起来，端到端速度才可能真正提升。

### 原因四：新模型也在同时改变算子需求

即使芯片不更新，大模型本身的变化也会创造新的算子工作。

过去的核心可能是标准 GEMM 和卷积；现在的热点则包括：

- FlashAttention 与 decode attention；
- MQA、GQA、MLA；
- MoE 的 dispatch、combine 和 grouped GEMM；
- FP8、FP4、INT8、INT4 量化；
- PagedAttention 和 KV Cache 管理；
- speculative decoding；
- 稀疏 Attention、长上下文与多模态算子。

硬件和模型是在共同演化的。芯片提供新的计算能力，模型提出新的执行模式，算子层负责把两者真正连接起来。

## 三、并不是所有算子都要重写

“每代芯片都有新工作”不等于“每代芯片都要重新实现全部基础运算”。实际情况通常可以分成三类。

### 第一类：旧实现已经足够好

对于常规、大尺寸、形状规整的 GEMM，新版 cuBLAS 或 CUTLASS 通常已经非常强。业务团队没有必要为了“自主可控”而重新写一个性能更差、维护成本更高的版本。

这时最合理的工作是：

- 升级库版本；
- 确认使用了正确的架构目标；
- 选择合适的 dtype 和算法；
- 做好基准测试与回归验证。

### 第二类：旧实现能跑，但没有走新硬件快路径

这是新架构早期最常见的情况。代码可以运行，却可能发生：

- 预编译包没有包含新 compute capability；
- 使用 PTX JIT 或兼容路径；
- 新 Tensor Core 指令没有启用；
- tile 参数仍按上一代 GPU 设置；
- 某些 shape 回退到通用 kernel；
- 新精度只支持部分算子。

这类工作重点不是重新发明算法，而是完成架构适配、调度调优和性能验证。

> **简单例子：可以运行，但走了回退路径**  
> 一个推理框架发现当前 GPU 没有对应的预编译 attention kernel，于是自动退回 PyTorch 的通用实现。模型不会报错，输出也正确，但性能可能明显下降。如果只看“程序跑通了”，就很容易误以为新架构已经得到完整支持。

### 第三类：现有库没有覆盖真实 workload

通用库必须兼顾大量设备、数据类型和输入形状，不可能对每个场景都最优。

例如，大型数据中心 GPU 常见高吞吐、大 batch 负载，而边缘设备可能更关心：

- batch 1–8 的低延迟；
- skinny GEMM（细长形状的矩阵乘）或 GEMV；
- 小矩阵和不规则 shape；
- 实时多模态流水线；
- 严格功耗限制；
- CPU、GPU、摄像头和其他加速单元之间的少拷贝；
- 长时间运行后的热稳态性能。

这时才真正需要场景特化的 kernel，甚至需要重新设计融合边界和执行流程。

## 四、新芯片发布后，算子工作分成哪几个层次？

### 第一层：芯片厂商与底层软件栈

这是最靠近硬件的一层，通常由 NVIDIA、AMD 或其他芯片厂商负责，包括：

- 编译器、汇编器和驱动支持；
- PTX/Cubin 与新架构目标；
- cuBLAS、cuDNN、CUTLASS；
- TensorRT、Transformer Engine；
- 通用 GEMM、卷积、Attention 和通信库。

这类工作需要详细的内部硬件资料，有时在芯片正式发布前就已经开始。

### 第二层：框架与开源生态

代表项目包括：

- PyTorch、JAX；
- Triton、TVM；
- FlashAttention、FlashInfer；
- vLLM、SGLang、TensorRT-LLM；
- DeepSpeed、Megatron-LM。

这里的工作包括：

- 新架构编译与打包；
- 新 dtype 和量化格式；
- 融合算子；
- 新的 attention、MoE 和 KV Cache kernel；
- 算法选择与 shape dispatch；
- 性能回归测试。

这也是开源贡献非常活跃的一层。很多新架构早期的问题，并不是芯片不能做，而是 wheel、构建脚本、架构列表或某个自定义算子尚未跟上。

### 第三层：模型与业务场景特化

这一层通常最接近真实产品，也最容易产生差异化：

- 为特定模型形状优化 grouped GEMM；
- 为某种 GQA/MLA 配置设计 decode attention；
- 把量化、矩阵乘、激活和残差连接融合；
- 针对实时机器人或端侧 VLM 减少数据复制；
- 在吞吐、延迟、功耗和精度之间做联合优化；
- 将通信与计算重叠，优化多卡或多节点执行。

通用库解决“多数情况下都能用”，场景特化解决“我的工作负载为什么仍然不够快”。

## 五、同一代架构的不同产品，为什么仍然需要不同优化？

即使两颗芯片属于同一个架构家族，也不代表它们拥有完全相同的资源配置和系统环境。

同代 GPU 往往会被做成不同产品形态，例如：

- 数据中心加速卡；
- 消费级显卡；
- 专业工作站显卡；
- 边缘或嵌入式 SoC；
- 面向汽车、机器人或工业设备的专用平台。

它们可能共享部分指令集和核心设计，但在以下方面存在明显差异：

- SM 数量与运行频率；
- 显存类型、容量和带宽；
- L2 缓存、共享内存和功耗预算；
- 是否拥有高速芯片间互联；
- CPU 与 GPU 是否共享内存；
- 散热条件和可持续运行频率；
- 典型 batch、输入形状和延迟目标。

因此，“支持某一代架构”只说明代码具有基本兼容性，并不能证明它在该架构的所有产品上都达到最优。

### 维度一：数据中心与边缘设备的目标不同

数据中心 GPU 通常追求高吞吐、大 batch 和多卡扩展，并配备高带宽显存和更充足的功耗预算。边缘设备则更关心小 batch、低延迟、能耗、体积和长时间稳定运行。

同一个 GEMM kernel 在高端数据中心 GPU 上可能依靠较大的 tile 获得高数据复用，但放到 SM 数量更少、片上资源配置不同的设备上，往往会因为并行度不足或资源占用过高而表现不佳——这时需要重新判断 tile 是否过大、CTA 是否足以填满设备、occupancy 是否受限，以及是否应改用针对小矩阵的实现。

### 维度二：大 batch 与小 batch 的最优解不同

大 batch 可以提供充足的并行任务，更容易摊薄启动和调度开销；小 batch 则经常遇到 GPU 吃不满的问题。

在线服务、交互式生成和实时应用常见 batch 1–8。此时，大矩阵乘的峰值性能不能直接代表实际响应速度，skinny GEMM、GEMV、小矩阵以及不规则 shape 可能更加重要。

所以，同一模型在离线吞吐测试和在线低延迟服务中，可能需要完全不同的 kernel 和调度策略。

> **简单例子：离线吞吐与在线聊天**  
> 离线生成任务可以把 64 个请求合成一个大 batch，让 GPU 长时间满负载；在线聊天可能一次只有一个请求，每生成一个 token 都要求尽快返回。前者更看重总 tokens/s，后者更看重单 token 延迟，同一个 kernel 未必能同时在两种场景下最优。

### 维度三：内存系统会改变算子的主要瓶颈

使用 HBM 的数据中心加速卡拥有很高的显存带宽，而采用 GDDR 或统一内存的产品具有不同的带宽、延迟和数据共享方式。

对于 GEMM 这类计算密集型算子，性能可能主要取决于 Tensor Core；对于归一化、激活、KV Cache 和数据格式转换等算子，性能则更可能由内存流量决定。

当计算能力增长速度超过内存带宽时，减少数据读写往往比增加算术吞吐更重要。

> **简单例子：融合为什么能加速**  
> `bias → GELU → quantize` 如果分成三个 kernel，中间结果至少要多次写入和读取显存；融合后，数据可以在寄存器中完成连续处理，只在最后写回一次。即使总计算量几乎没变，内存流量和启动次数都会减少。

常见手段包括：

- 融合多个算子；
- 避免物化中间张量；
- 使用更紧凑的数据类型；
- 改善连续访问与缓存命中；
- 让中间结果尽量停留在寄存器或共享内存中。

### 维度四：互联条件会影响单算子之外的设计

在拥有高速 GPU 互联的系统中，可以更积极地采用张量并行、专家并行和细粒度通信；在只依赖 PCIe 或以太网的系统中，通信成本可能迅速超过计算收益。

这时，优化重点会从单卡 kernel 扩展到：

- 减少通信数据量；
- 调整模型分区；
- 合并小消息；
- 通信与计算重叠；
- 融合通信前后的量化、重排和归约；
- 根据网络带宽选择并行策略。

因此，算子性能不能脱离系统拓扑孤立评价。

### 维度五：功耗和热稳态也会改变最优实现

峰值性能通常是在理想频率和短时间测试下得到的，但很多设备需要在固定功耗或温度条件下长期运行。

一个追求最高瞬时吞吐的 kernel，可能导致功耗和温度快速上升，随后触发降频；另一个峰值略低但数据搬运更少、执行更稳定的实现，反而可能拥有更好的持续吞吐和能效。

所以在受功耗约束的场景中，除了平均速度，还应测量：

- p95/p99 延迟；
- 每瓦性能；
- 每次请求或每个 token 的能耗；
- 长时间运行后的频率和吞吐；
- 不同功耗模式下的性能变化。

这说明产品级优化并不是“为每张卡单独写一套代码”，而是在统一实现之外建立合理的架构检测、参数选择和 kernel dispatch 机制。

## 六、算子开发真正的护城河是什么？

如果把算子开发简单等同于“会写 CUDA 语法”，就很容易高估这项技能的价值——它的门槛其实没那么高，也很容易被工具替代。

Triton、CUTLASS、CuTe DSL、TVM 和各种自动调优工具都在降低 kernel 开发门槛。AI 代码生成也可以快速写出一个能运行的 kernel。

但真正困难的部分仍然是：

1. **识别瓶颈**：到底受计算、内存、同步、启动还是通信限制？
2. **建立成本模型**：知道理论上最多能提升多少，而不是盲目调参；
3. **选择优化层级**：应该改 kernel、数据布局、融合边界、调度器，还是模型算法？
4. **理解硬件约束**：寄存器、共享内存、occupancy 和数据复用如何相互影响？
5. **证明端到端收益**：microbenchmark 变快，真实模型是否真的变快？
6. **控制工程复杂度**：性能提升是否值得新增的维护成本和兼容性风险？

所以高水平算子工程师的价值并不是“手写代码比库多”，而是能够回答：

> 为什么这个 workload 在这颗芯片上慢？最值得改的是哪一层？如何用最小的工程代价获得可验证的端到端收益？

## 七、新芯片发布后，一套可靠的算子开发流程

### 第一步：先确认是否真的存在缺口

不要看到新架构就立刻重写算子。首先检查：

- 官方库是否已经支持；
- 当前程序实际调用哪个 kernel；
- 是否发生 fallback（自动回退到通用实现）；
- 预编译包是否包含正确架构；
- 最新版本是否已经解决问题。

### 第二步：建立可信 baseline

记录完整环境：

- 芯片与功耗模式；
- 驱动、CUDA、框架和库版本；
- dtype、shape、batch、上下文长度；
- warmup、重复次数和同步方法；
- 正确性容差；
- 温度与频率状态。

没有可信 baseline，所谓“提升 30%”往往没有意义。

> **简单例子：错误的 30% 提升**  
> baseline 在 GPU 未预热、频率较低时只测了一次，优化版却先运行了几十轮再取最好结果，看起来可能快了 30%。但统一 warmup、同步和统计口径后，真实差距也许只有 5%。因此，测量方法本身就是性能工程的一部分。

### 第三步：用 profiler 找真正热点

通过 Nsight Systems、Nsight Compute 或框架 profiler 回答：

- 哪些 kernel 占用总时间最多？
- GPU 是否有空洞？
- DRAM、L2 和 SM 利用率如何？
- Tensor Core 是否工作？
- kernel 是否过于碎片化？
- 通信和计算能否重叠？

### 第四步：建立理论上限

使用 Roofline、带宽上限和计算量估算，判断 kernel 属于：

- compute-bound；
- memory-bound；
- latency-bound；
- launch-bound；
- communication-bound。

不同瓶颈需要不同手段。给 memory-bound kernel 增加更多计算单元通常没有帮助；给 launch-bound workload 继续优化单个 kernel 的 FLOPS 也可能收效甚微。

> **简单例子：先判断瓶颈再动手**  
> 如果 profiler 显示一个向量加法已经接近显存带宽上限，那么继续优化乘加指令通常不会明显变快；更有效的办法可能是把它与前后操作融合，少读写一次显存。反过来，如果 Tensor Core 利用率很低，就要检查 tile、数据类型和矩阵指令路径。

### 第五步：从最便宜的优化开始

一个合理顺序是：

1. 使用更新的官方库；
2. 调整 shape、layout 和算法选择；
3. 做 kernel fusion；
4. 用 Triton 快速验证；
5. 必要时再用 CUDA/CUTLASS 深度优化；
6. 最后考虑算法级改变。

### 第六步：回到端到端系统验证

最终至少要比较：

- 单算子 latency；
- TTFT 和 TPOT；
- tokens/s；
- p95/p99 延迟；
- 峰值内存；
- 功耗和每 token 能耗；
- 精度或模型质量；
- 不同输入和长时间运行的稳定性。

只有当真实应用变快，算子优化才算闭环。

## 八、这类工作会不会被自动编译器和 AI 取代？

自动调优和 AI 生成 kernel 会减少机械工作，例如：

- 生成基础 CUDA/Triton 代码；
- 搜索 tile 和 num warps；
- 完成常见算子融合；
- 迁移简单的架构参数；
- 自动跑 correctness 和 benchmark。

但新硬件越复杂，设计空间反而越大。工具可以搜索一个已经定义好的空间，却仍然需要人来决定：

- 应该搜索什么；
- 正确的目标函数是什么；
- 哪些约束不能违反；
- 单算子与端到端指标为什么冲突；
- 优化应该发生在模型、编译器、kernel 还是系统层。

未来的算子工程师可能更少地逐行手写所有代码，更多地负责**硬件感知的设计、测量、搜索空间构造和跨层决策**。

---

## 九、结论：新芯片持续创造工作，但工作内容正在升级

每一代芯片发布后，算子开发确实都会迎来一轮新工作，因为：

- 新指令需要软件使用；
- 最优 tile 和流水线发生变化；
- 新数据类型需要完整软件链；
- 新模型引入新的计算模式；
- 不同产品形态拥有不同的内存、功耗和互联约束。

但这并不意味着所有算子都要重新写。成熟基础算子应该优先使用官方库；真正值得投入的，是那些没有覆盖新架构快路径、没有适配真实 shape，或者无法满足特定场景约束的部分。

因此，算子开发最重要的能力不是追着架构名学习一套新语法，而是形成一套稳定的方法：

> 理解硬件成本模型，测出真实瓶颈，判断应该优化哪一层，并把硬件能力转化成端到端可验证的性能、能效或延迟收益。

这一规律并不局限于某一家厂商：本文多以 NVIDIA 生态举例，但 AMD ROCm 以及其他 AI 加速器同样如此——只要硬件在持续演进，算子层就需要持续适配。

新芯片会不断发布，指令也会不断变化。但只要计算、内存和通信之间仍然存在不平衡，通用实现就不可能覆盖所有模型与场景——高性能算子开发不会消失，只会从“把程序写出来”升级为“让算法、编译器、kernel 和系统在新硬件上共同达到最优”。
